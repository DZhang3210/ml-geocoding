## Open questions
- **Pairs-per-street-group cap for Case 1 hard negatives — deliberately deferred 2026-09-15.** `NUM_NEGATIVE` (currently 4 candidate ids per exact-street-identity group, giving up to `C(4,2)=6` possible pairs per group) is a placeholder, not a final value. David's call: figure out the actual number once total dataset size/class balance (positives vs. negatives) is known, rather than picking a number now — revisit when building the final pairs table.
- **Hard-negative proportion: train vs. eval should NOT use the same policy — flagged 2026-09-15, not yet resolved, revisit at train/val/test split time.** Deliberately oversampling hard negatives (well beyond their true real-world frequency) is good, standard practice for *training* — easy examples contribute near-zero gradient signal once the model already gets them right, so hard cases are where the useful learning signal actually is. But doing the same for *evaluation* is a problem: a hard-case-biased test set understates real-world performance, the mirror image of the already-logged "inflated F1 from too-easy negatives" risk. Planned resolution: don't rely on one blended headline metric — stratify reported results by case difficulty (easy vs. hard, ties into Step 6's error-analysis framing) rather than picking one single "true" proportion for both training and evaluation. Needs a concrete decision when the train/val/test split is actually built (e.g. keep val/test closer to a realistic mix, or keep the same hard-negative-heavy mix everywhere but report metrics broken out by difficulty).
- **Character-level replacement corruption — design settled 2026-09-15, not yet built.** Scoped to base `StreetName` only (disjoint from abbreviation-substitution's fields, avoids ordering conflicts); one per-character roll (~10%) decides if anything happens, a second coin-flip decides substitute-vs-delete; substituted character is uniformly random a-z. Two realism refinements were discussed and deliberately deferred as documented simplifications rather than built now: (1) FEBRL-style keyboard-adjacency-weighted substitution (vs. uniform random) and (2) correlated/"clumped" error probability (a Markov-chain-style model where an edit at position i boosts the probability of another edit nearby, matching how real human typos cluster rather than scatter independently) — both are real, literature-grounded ideas worth revisiting after a first working version exists.
- **Possible baseline-inflation risk from character-level corruption — flagged 2026-09-15, deferred as a post-mortem/limitations item, not yet resolved.** Character replacement/deletion are literally 2 of the 3 primitive Levenshtein edit operations (insertion is the third, not currently planned). Comber & Arribas-Bel's Step 1 baseline uses edit-distance-style similarity as its core feature, so synthetic positive pairs generated via small random character edits could make an edit-distance-based classifier look artificially strong — the label-generating process and the detection feature would be suspiciously aligned, similar in spirit to the inflated-F1 concern already noted for the original (discarded) Step 1 attempt. Abbreviation-substitution corruption (the other method already built) doesn't have this problem nearly as much — those are multi-character, semantically-motivated edits (e.g. `ST`→`STREET` is edit-distance 4), not small random perturbations. Decision: proceed with building character-level corruption as planned for now; revisit this explicitly once Step 1's baseline is built and evaluated against these pairs — if it performs suspiciously well specifically on character-corrupted pairs, that's the signal to dig into this. Worth writing up regardless as a limitations/methodology point in the eventual Step 7 writeup.
- **Hard-negative pair generation** (same street/different number, or same number/similar street name, per the roadmap's Step 2 instructions) — not started yet; only positive-pair corruption (abbreviation substitution) has been built so far.
- **Multiple corrupted variants per original row?** David indicated "maybe more" later (2026-09-15) — currently `corrupt_rows` produces exactly one corrupted row per original (1:1), so `original_id` alone is a unique key in the corrupted dataframe. If multiple variants per source row are added later, `original_id` will stop being unique and a separate, independent `id` for each corrupted row will be needed alongside it.
- **Corruption-method metadata tracking** — discussed as valuable for Step 6 error analysis (knowing which corruption(s) actually fired per generated pair, not just before/after strings) but not yet implemented in `corrupt_rows`.
- **`sfx_abrev_lookup["WALK"]` still contains a duplicate (`["WALKS", "WALKS"]`)** — an artifact of the USPS source table having two rows collapse to the same commonly-used spelling. Not deduped; causes a minor, low-stakes sampling-weight bias (that value is ~2x as likely to be picked) rather than a correctness bug. Left as-is per discussion (2026-09-15) — revisit if it turns out to matter.

## Resolved questions
- **Case 2 (fuzzy blocking) similarity threshold — resolved 2026-09-15: 0.85 Jaro-Winkler.** Decided empirically, not guessed: computed each unique (stripped, base) street name's best Jaro-Winkler match against every other unique name, looked at the percentile distribution and how many names would have zero qualifying match at several candidate thresholds (0.70→12/1149 with none, 0.75→40, 0.80→191, 0.85→479, 0.90→838), then sanity-checked against real examples at each score level (e.g. `ALDEN`/`ARDEN` and `BLUE SPRUCE`/`BLUE ROCK` at ~0.88 read as genuinely plausible mix-ups; `DOWNS`/`DOLSEN` at ~0.79 did not, despite a similar-looking score) to find where the threshold actually starts meaning "looks confusable" rather than just "shares some letters." Also discovered along the way: comparing *full* unstripped street names (`"MAIN ST"`) gives a *lower* no-match rate (8.3%) than the stripped base names (16.6%) used for blocking — the opposite of what you'd naively expect — because ~24 common suffixes covering nearly all streets inflate full-name similarity scores with "free," coincidental matching characters unrelated to real name similarity (and Jaro-Winkler's explicit prefix bonus would do the same for shared prefixes, though directionals are too rare in this dataset for that to matter much here). Confirms using the stripped base name for blocking is the more meaningful choice, not just a convenience.
- **`EXT` as a trailing street-name qualifier (e.g. `DUNN AVE EXT`) — resolved 2026-09-15.** Checked against the full dataset (not just the deduplicated preview): `EXT` appears in exactly 2 rows, both `DUNN AVE EXT`, always in the trailing/suffix position — never as a prefix, never mid-string. Added `is_extensional` (boolean) + stripped `EXT` from `StreetName`, same pattern as the `Directional` column.
- **ZIP code leading-zero loss — resolved 2026-09-15.** `ZipCode` values were silently losing their leading zero (`06903` → `6903`). Traced the full chain: the shapefile field is a character type and stores `'06903'` correctly; `convert_file_to_csv.py`'s `output.csv` is also correct (`06903` written verbatim). The bug was `pd.read_csv("./output.csv")`'s automatic dtype inference treating the unquoted numeric-looking column as `int64`. Fixed via `dtype={"ZipCode": str}` at read time.
