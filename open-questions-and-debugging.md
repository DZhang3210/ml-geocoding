Decision: proceed with building character-level corruption as planned for now; revisit this explicitly once Step 1's baseline is built and evaluated against these pairs — if it performs suspiciously well specifically on character-corrupted pairs, that's the signal to dig into this. ## Resolved questions
- **Symmetric corruption for negative pairs — RESOLVED 2026-09-17 (supersedes the 2026-09-16 "randomly pick one side" decision).** David's real-world framing: one side is always the known-clean canonical reference, the other is always the potentially-dirty query — so "one side always corrupted" isn't a spurious shortcut, it's representative, and leaving negatives fully clean would itself be unrealistic (a real non-match is still a messy query vs. a clean record). Resolution: deterministic, not random — column `b` is always the corrupted-lookup side, across positive, easy-negative, and hard-negative tables alike. Explicitly flagged as a real scope choice, not free: Step 3's planned siamese architecture shares encoder weights, which normally implies a symmetric (order-invariant) matching task; a stable "b is always dirty" pattern nudges the project toward an asymmetric canonical-vs-query framing instead. Revisit if later error analysis suggests the model is leaning on side-identity rather than genuine address semantics — flip back to random-side if so.
- **Hard-negative/easy-negative/positive proportion for the final combined training table — RESOLVED 2026-09-17: 1:1:1 for now.** `_generate_training_data()` calls all three generators at `amount=14818` each. Chosen for simplicity over deliberately overweighting hard negatives (which the project's own notes elsewhere argue are more valuable for training signal, since easy examples contribute near-zero gradient once the model already gets them right) — revisit if training shows the model isn't learning much from a large share of easy cases.
- **Location-based (id-based) train/val/test split — RESOLVED 2026-09-17.** First instinct (`train_test_split` called directly on the combined pair-table) was caught as insufficient before being built out further — it has no concept of `id_a`/`id_b` repeating across rows, so it can't prevent the same address appearing in both train and test via different pair-rows. Correct approach: `train_test_split` the **id space** (`range(len(new_df))`, 28,294 unique addresses) via two chained calls (~68/17/15 train/val/test), then filter the combined table into three subsets requiring *both* `id_a` and `id_b` to belong to the same id-group (`.isin() & .isin()`), dropping any row whose two ids land in different groups. This guarantees no id overlap across the three final row-tables *by construction* — nothing to separately "check and remove" afterward, since a row is either assigned to exactly one split or dropped, never assigned to two. Result: 23,900 train / 3,356 val / 2,866 test = 30,122 of 44,450 rows retained; see the negative-row-loss open question above for the accepted tradeoff.
- **Pairs-per-street-group cap for Case 1 hard negatives — resolved 2026-09-16: `NUM_NEGATIVE=4`, random sample.** Was deliberately deferred on 2026-09-15 pending real numbers. Uncapped, Case 1 produced 932,661 pairs with the top 5 streets alone contributing ~35% of them (quadratic blowup from a handful of very long streets) — capping the candidate pool to 4 ids per group before pairing (`C(4,2)=6` max per group) brought it down to 7,334 pairs. Initially sliced `lst[:4]` (deterministic, biased toward whatever's first in the group's insertion order); switched to `random.sample(lst, min(len(lst), NUM_NEGATIVE))` once that bias was flagged. Confirmed zero duplicate pairs.
- **Hard-negative pair generation (Case 1 + Case 2 → actual `(id_a, id_b, label)` rows) — resolved 2026-09-16.** Case 1: `[[min(a,b), max(a,b)] for a,b in itertools.combinations(random.sample(lst, min(len(lst), NUM_NEGATIVE)), 2)]` per exact-street-identity group → 7,334 pairs. Case 2: switched `jw_lookup` from name-keyed to id-keyed (`{(min(aid,bid),max(aid,bid)): score}`), built inside a corrected `Address`-only `groupby` (an earlier `groupby(["StreetName","Address"])` version forced `a==b` self-pairs — see Debugging log), with composite scoring (raw Jaro-Winkler + directional/extension/is_extensional bonuses) filtered at ≥0.85 → 15,435 pairs. Combined and deduped via `set(map(tuple, train_df_lst))` → ~22,767 pairs, confirmed via a component-ablation and concentration analysis that neither case's final output is dominated by a small number of groups. See progress-log.md's 2026-09-16 entry for the full debugging path (multiple real bugs along the way, not just a clean build).
- **Case 2 (fuzzy blocking) similarity threshold — resolved 2026-09-15: 0.85 Jaro-Winkler.** Decided empirically, not guessed: computed each unique (stripped, base) street name's best Jaro-Winkler match against every other unique name, looked at the percentile distribution and how many names would have zero qualifying match at several candidate thresholds (0.70→12/1149 with none, 0.75→40, 0.80→191, 0.85→479, 0.90→838), then sanity-checked against real examples at each score level (e.g. `ALDEN`/`ARDEN` and `BLUE SPRUCE`/`BLUE ROCK` at ~0.88 read as genuinely plausible mix-ups; `DOWNS`/`DOLSEN` at ~0.79 did not, despite a similar-looking score) to find where the threshold actually starts meaning "looks confusable" rather than just "shares some letters." Also discovered along the way: comparing *full* unstripped street names (`"MAIN ST"`) gives a *lower* no-match rate (8.3%) than the stripped base names (16.6%) used for blocking — the opposite of what you'd naively expect — because ~24 common suffixes covering nearly all streets inflate full-name similarity scores with "free," coincidental matching characters unrelated to real name similarity (and Jaro-Winkler's explicit prefix bonus would do the same for shared prefixes, though directionals are too rare in this dataset for that to matter much here). Confirms using the stripped base name for blocking is the more meaningful choice, not just a convenience.
- **`EXT` as a trailing street-name qualifier (e.g. `DUNN AVE EXT`) — resolved 2026-09-15.** Checked against the full dataset (not just the deduplicated preview): `EXT` appears in exactly 2 rows, both `DUNN AVE EXT`, always in the trailing/suffix position — never as a prefix, never mid-string. Added `is_extensional` (boolean) + stripped `EXT` from `StreetName`, same pattern as the `Directional` column.
- **ZIP code leading-zero loss — resolved 2026-09-15.** `ZipCode` values were silently losing their leading zero (`06903` → `6903`). Traced the full chain: the shapefile field is a character type and stores `'06903'` correctly; `convert_file_to_csv.py`'s `output.csv` is also correct (`06903` written verbatim). The bug was `pd.read_csv("./output.csv")`'s automatic dtype inference treating the unquoted numeric-looking column as `int64`. Fixed via `dtype={"ZipCode": str}` at read time.
- **Train/val/test label-ratio mismatch (58/42 vs. 77/23) — RESOLVED 2026-09-21.** Root cause: the original split-then-filter method retains negatives with probability `≈p_split²` but positives with probability 1, so smaller splits (val, test) lost negatives far more aggressively than train — producing different label priors per split despite the 2026-09-17 notes describing an aggregate ~1:1 balance. Fixed by restructuring to split the id space first, then generating positives/negatives independently within each split's own id pool. See progress-log.md's 2026-09-21 Step 2 entry for full detail.
- **Target positive:negative ratio — RESOLVED 2026-09-21: ~1:9 (precisely ~1:8.44), grounded in Comber & Arribas-Bel (2019)'s reported 110,742:934,150 pair counts, applied uniformly across train/val/test** (not split differently between train and eval — see the still-open "hard-negative proportion: train vs. eval" question above, deliberately deferred rather than resolved simultaneously with this one). Verified post-rebuild: train 9.00:1, val 9.07:1, test 9.03:1.
