## Review notes (Claude, 2026-11-13)
- **What it is:** a geocoding-*system* review (parse → store → retrieve → interpolate), not an address-matching review. Matching is one sub-component ("retrieval", §4.2.3, ~2.5 pages). Called "systematic" but no search protocol, databases, counts or inclusion criteria are reported (unlike Cruz 2022's PRISMA).
- **Taxonomy of matching (§4.2.3):** classifier type: deterministic (hand weights, Goldberg & Cockburn 2010) → probabilistic (Fellegi–Sunter; TF-IDF / BM25 in Elasticsearch) → machine learning (new category they define). Similarity type orthogonal: phonetic / string / vector.
- **Address matching since 2021, as covered here:** only three papers. Rezaei Ghahroodi et al. 2024 (string similarity + SVM, Iran census); Duarte & Oliveira 2023a (DistilBERT bi-encoder top-10 + transformer re-rank, Portugal = our Step 5 paper) and 2023b (multiple in-batch negatives loss). Not cited: Quan 2024, Ramani & Borrajo 2024, Kilic 2024, any LLM-as-matcher work.
- **LLMs:** applied only to parsing / standardization (Yin et al. 2023 ChatGPT benchmark; Huang et al. 2024 GeoAgent; Li et al. 2023 BERT parser — text calls it "AddressBERT", the reference is "EnEx-FP", so the citation is muddled). For matching, LLMs appear only as a §5.3 vision (whole-address embeddings, text + spatial distance in one loss). They count BERT as an "LLM".
- **Benchmarks / hard cases:** no public address-*matching* benchmark named. The only benchmark is Yin et al. 2023 (US addresses with 21 input-error categories mined from production logs, built for **parsing**). §5.1 says results across geocoding papers are incomparable for lack of standard datasets and metrics and calls for one; p.16 says classifiers should be compared "on a unified data set". No hard-negative / per-slice evaluation anywhere; errors are framed as noisy *inputs* (typos, omissions, synonyms), never as near-miss *non-matches* (same street other number, look-alike street).
- **Authors / Quan link:** Shaohua Wang (author 10) is at the State Key Laboratory of Remote Sensing and Digital Earth, Aerospace Information Research Institute (AIR), CAS. Quan et al. 2024 are at AIR, CAS (lab not named). Same institute, no shared authors, and Yin does not cite Quan.
- **Our steps in its taxonomy:** 1 / 1b = string similarity + ML classifier · 2c libpostal = parsing + deterministic rule · 3 siamese, 4 ESIM, 5 DistilBERT = machine learning with vector similarity. Our setting is pair classification, theirs is retrieval against a reference gazetteer.

## Discussion takeaways (Claude)
Settled with David, 2026-11-14 (read §4.2.3, §5.1, §5.3):

| Step D candidate | Yin 2025 says | Status from this paper |
|---|---|---|
| Open real US cross-source address-pair benchmark | No address-matching benchmark named; §5.1 (p.21) and p.16 call for a unified, open dataset. Their only benchmark (Yin et al. 2023) is for parsing, US, synthetic input errors | Supports "new"; citable 2025 motivation (cite as arXiv preprint) |
| Results per hard-negative slice | Errors framed only as noisy *inputs* (typos, omissions, synonyms); near-miss *non-matches* never mentioned | Supports "new"; complementary to their wished-for benchmark, not the same thing |
| Many models on identical splits | p.16: classifiers "should be systematically evaluated on a unified data set"; no such comparison cited | Supports "new" (weak: a call, not a gap analysis) |
| Failure modes (missing number, ZIP variation) | Not discussed | No evidence either way |

- **Caveat:** "not in Yin" ≠ "not done". It misses Quan 2024, Ramani & Borrajo 2024, Kilic 2024, and reports no search method. It's evidence of a gap only together with the other searches.
- **Taxonomy for the related-work section:** matching = Classifier(Similarity). Classifier types: deterministic (hand weights), probabilistic (weights from value rarity in the reference data, no labels: Fellegi–Sunter per parsed field, TF-IDF / BM25 per token), machine learning (learned from labelled pairs; = deterministic with learned weights). Our steps: 1/1b ML on string similarity; 2c parse + rule; 3–5 ML on vectors.
- **If a retrieval setting is added (Step D item 3):** a BM25 baseline (Elasticsearch-style, as in Pelias / Photon) is the one reviewers from the geocoding community will expect; Duarte 2023 already compares against it. Probabilistic weighting should fail on case1 (a rare shared street name pulls towards "match").
- **LLMs:** "LLM" here means any transformer (BERT counted). LLMs are applied to parsing only; whole-address embedding retrieval = Duarte 2023 = our 5a. The only new idea is a joint text + spatial-distance loss (p.22), close to the optional GeoBERT stretch; not a Step D candidate.
- **Segmentation (David):** parse-then-compare assumes a reliable parser, which is optimistic outside clean formatted addresses; Yin p.18 H1 (segment by components = better) is a hypothesis without evidence. Our own evidence: 2c vs 1b (`06_compare_libpostal_and_dumb.ipynb`).
