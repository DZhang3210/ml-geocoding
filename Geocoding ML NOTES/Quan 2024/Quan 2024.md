# Quan, Chang, Liang, Qiao & Wang (2024)

**Title:** "A Novel Address-Matching Framework Based on Region Proposal" (RPAM)
**Venue:** ISPRS Int. J. Geo-Inf. 13(4):138 (21 April 2024) — roadmap Step 8's paper
**Link:** https://doi.org/10.3390/ijgi13040138 · PDF: `papers/step8_quan-etal-2024_region-proposal-address-matching.pdf`

**Not a survey.** The roadmap calls it "2024 survey" / "field taxonomy"; it is a method paper with a two-page related-work section. The field taxonomy has to come from Cruz et al. 2022 and Yin et al. 2025.

## Review notes (Claude, 2026-11-13)
- **Task:** retrieval, not pair classification. Query text → one POI out of 287k (Beijing Chaoyang). Metrics Recall@k, MRR@k, Accuracy@N km.
- **Method:** stage 1 = RoBERTa-wwm classifier predicts the S2 cell (levels 11/12/13, loss weights 0.1/0.2/0.7, score = p11·p12·p13) + 1 km buffer → candidates; stage 2 = shared-weight bi-encoder, cosine, Faiss top-k.
- **Data:** queries are synthetic (synonym swap, element removal, name/address order swap of the POI's own text); 95/5 split by POI; data "on request".
- **Result:** Recall@1 +0.55 to +1.56 pts across four encoders; distance accuracy gains larger (+1.8 to +5.7 @0.5 km). No seeds, no variance.
- **Relation to us:** stage 1 = a learned version of our ZIP blocking; stage 2 = Step 5a. Supports the "retrieval setting" option in Step D; its taxonomy (grid prediction vs address matching) is a geocoding one, not an address-matching one.

## Discussion takeaways (Claude, 2026-11-14)
- **Step D answer (David): retrieval setting deferred, not rejected.** He wants to read more of the professors' work (`professor-research.md` §3) before deciding: building the per-ZIP candidate database is real work and only worth it if the target labs care about retrieval.
- **David's reasoning:** for: every address in the ZIP becomes a natural negative, so no hand-built negatives are needed at eval time. Against: fixed pairs isolate each negative type (our per-slice results); `case2s` street swaps don't exist in Overture, so retrieval can't test them; training still needs pairs anyway.
- **Points settled in discussion:** (1) Quan's contribution (learned stage 1) is the part we don't need, since ZIP is a free, exact block; only the setting and metrics would transfer. (2) The slices survive in retrieval as "what outranked the truth": label the rank-1 wrong candidate with `add_number_street` (case1 / case2 / other). (3) Cost: string features and ESIM/5b can't be precomputed, but within a ZIP block cheap scorers are fine (ms per query); only the cross-encoder needs a top-k cut.
- **Open check before deciding:** Overture addresses per ZIP (median, max) — the number that sets retrieval's cost. David runs it in a Diagnostics cell.
- **Concepts:** Recall@k vs classification recall (one relevant item per query) — corrected; MRR = mean of reciprocal ranks, not distance (worked example 1 / 4 / miss → MRR@5 0.42 vs Recall@5 0.67) — understood. Paper misstates MRR as "reciprocal of the average rank" (§4.2). Initially read §4.2 as "loss at k" measuring distance (conflated with Accuracy@N km).
- **Paper's standing (agreed):** incremental, not cutting edge: +0.5–1.5 pts Recall@1, single runs, synthetic queries, stage-2 encoders never fine-tuned on matching, data on request. Useful as a template for a retrieval setting, not a result to beat. Table 5 ceiling (98.5% at 1 km) = ~1.5% of queries unreachable after stage 1 — David's catch.
