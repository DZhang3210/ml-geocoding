## Concepts already explained / understood
- **pandas `.str` accessor vs. indexing a Series directly** — `series.str.split()` returns a Series of lists; `[-1]`/`[0]` on the *Series itself* does label-based lookup against its index (raises `KeyError` on a RangeIndex, since there's no label `-1`), not "get the last element of each row's list." Use `.str[-1]`/`.str[0]` to index into each row's list elementwise. Covered 2026-09-14.
- **`Series.map()` as a lookup/join against another Series or dict** — `value_counts()` returns a Series shaped exactly like a lookup table (index = unique value, value = count); `.map()` uses that to replace each row's value with its corresponding count (or any other keyed lookup). Covered 2026-09-14.
- **Boolean mask combination: `&`/`|` vs. Python's `and`/`or`** — `and`/`or` try to evaluate the truthiness of an entire Series (ambiguous for length >1, raises `ValueError`), while `&`/`|` are pandas-overridden operators that combine two boolean Series elementwise. Operator precedence also means each condition needs its own parentheses when combined this way. Covered 2026-09-14 (surfaced through a real `ValueError: truth value of a Series is ambiguous` debugging session).
- **`df.copy()` deep-copies by default** — no need for Python's `copy.deepcopy()`; `.copy()` already does what's needed to avoid two names pointing at the same underlying DataFrame. Covered 2026-09-14.
- **`.apply()` mechanics** — runs a function once per row/value; returning a single value produces one new column, returning a `pd.Series` with named fields lets pandas expand it into multiple new columns at once (`df[["a","b"]] = series.apply(fn)`). Covered 2026-09-14.
- **`sort_values()` vs. `sort_index()`**, and that `value_counts()` is already sorted descending by count by default. Covered 2026-09-14.
- **`DataFrame.insert()` is in-place/mutating and returns `None`** — same category as `list.sort()`. Caught as a real bug: `csv["id"] = csv.insert(0, "id", [...])` first correctly inserts `id` via the side effect, then immediately overwrites it with `None` (the method's return value). Fix: just call `.insert()` on its own, no outer assignment. Covered 2026-09-15.
- **Notebook cell statefulness — output can silently go stale relative to source.** If a cell mutates a persistent variable in place (or partially, across a multi-line cell) and gets edited/rerun, the *displayed* output can reflect a stale prior run rather than the current code — hit repeatedly this session (an `EXT` detection false-negative from rerunning a cell that had already stripped `EXT` the first time; a `groupby().to_dict()` cell displaying a stale raw DataFrame instead of the actual dict; `corrupt_rows` appearing to produce unchanged output twice in a row after real fixes). Diagnosed each time by independently reproducing the *current* saved source outside the notebook and comparing to the notebook's displayed output. Covered/reinforced multiple times, 2026-09-15.
- **Python global-namespace shadowing of builtins.** `for key, list in some_dict.items():` rebinds the name `list` in the whole notebook session, not just the loop body — a later, unrelated call to `.apply(list)` then breaks with `TypeError: unhashable type: 'list'`, because `list` no longer refers to the builtin constructor. Fix required both renaming the loop variable *and* restarting the kernel, since the corrupted global binding persists in memory until restart. Covered 2026-09-15.
- **`list.find()` doesn't exist; `list.index()` raises `ValueError` if not found (unlike `str.find()`'s `-1`); and `if index:` is a truthiness check, not a found/not-found check** — silently wrong when a match is found at position 0 (`if 0:` is `False`). Covered 2026-09-15.
- **Row-as-Series round-tripping:** a single row pulled from a DataFrame (`df.loc[i]`, or the second element of an `iterrows()` tuple) collapses to one shared `dtype` (usually `object`), but `pd.DataFrame(list_of_row_series_or_dicts)` correctly re-infers proper per-column dtypes on reconstruction — verified this empirically rather than assuming. The real risk going Series→DataFrame isn't dtype loss; it's implicit, silently-permissive index alignment (a typo'd/missing key doesn't error, it just produces `NaN` or a stray column) and orientation ambiguity (`.to_frame().T` needed to turn a Series into a one-row rather than one-column DataFrame). Covered 2026-09-15.
- **`df.iterrows()` yields `(index, Series)` tuples**, not just the Series — `for row in df.iterrows()` gives you the whole tuple; forgetting to unpack (`for _, row in df.iterrows()`) causes e.g. `row.copy()` to fail with `AttributeError: 'tuple' object has no attribute 'copy'` since tuples have no `.copy()`. Covered 2026-09-15.
- **`DataFrame.groupby()` as the idiomatic "for each unique value, act on all its rows" iterator** — directly iterable as `(key, group_df)` pairs, and collapses to a one-liner via `.groupby(col)[other_col].apply(list).to_dict()` when you just want the finished lookup dict rather than an explicit loop. Covered 2026-09-15.
- **`DataFrame.rename()` (like most pandas ops) returns a new object rather than mutating in place** — needs reassignment. Also caught a real bug from reusing one variable name for two different DataFrames in the same function: `new_df = pd.DataFrame(corrupted_rows); new_df = df.rename(...)` — the second line overwrote the actual corrupted result with a renamed copy of the original, uncorrupted input. Covered 2026-09-15.
- **`itertools.combinations(iterable, r)`** — `r` is required, not optional; generates every unique r-length combination without duplicates/self-pairs/reversed-order repeats, replacing manual nested-loop index bookkeeping. Covered 2026-09-15.
- **Iterating a plain dict directly yields only its keys, not `(key, value)` pairs** — need `.items()` for both; hit as a real bug trying to unpack a single dict key (itself a multi-element tuple) into a `(group_key, value)` pattern. Covered 2026-09-15.
- **`collections.defaultdict(list)`** — auto-initializes a missing key to an empty list on first access, avoiding `KeyError` from `.append()`-ing to a key a plain `{}` doesn't have yet. Covered 2026-09-15 (after hitting the KeyError firsthand first).
- **Rejection sampling** — to enforce a constraint (e.g. "at most half the characters get edited") without biasing *which* elements get selected, regenerate the whole random draw and discard it if it violates the constraint, rather than truncating/stopping early once a budget is hit (which biases toward whatever gets processed first). Covered 2026-09-15, motivated by David's own observation that a sequential "stop once you hit the cap" approach would bias toward earlier characters.
- **Blocking (record-linkage term) serves two different purposes, and this project only needs one of them.** In a deployed system, blocking narrows a large reference database down to a cheap candidate set before expensive pairwise comparison (bounding *retrieval cost*) — genuinely O(n²)-avoidance at scale. In this project, "blocking" is used purely offline, as a *training-data construction* technique to deliberately find pairs that are hard/confusable, with no retrieval-cost concern at all (the model itself only ever does pairwise classification, never search) — so a top-K cap (useful for bounding live retrieval) isn't actually needed here; an absolute similarity/exactness threshold alone is the right tool. Covered 2026-09-15, worked out over several turns of discussion.
- **String-similarity metric families and what "typed like hot garbage" actually needs** — Levenshtein/edit distance costs a transposition (e.g. `teh`/`the`) as 2 operations; Damerau-Levenshtein fixes that by counting it as 1; Jaro-Winkler (used in Comber & Arribas-Bel, this project's Step 1 paper) is built for short, noisy strings like names/addresses and adds an explicit bonus for shared prefixes; token/set-based metrics (Jaccard, cosine, Monge-Elkan, ...) are robust to word-*order* changes but not within-token typos. Real systems (Lee et al. 2020/Step 1b) typically compute a bank of several metrics rather than picking one. Covered 2026-09-15.
- **Hard-negative mining: train-time oversampling of hard examples is standard/good practice, but the same policy shouldn't be used for evaluation.** Easy examples contribute near-zero gradient signal once a model already gets them right, so training benefits from deliberately biasing toward hard cases well beyond their true frequency — but a test set biased the same way *understates* real-world performance, mirroring (in the opposite direction) the already-known "inflated F1 from too-easy negatives" risk. Resolution isn't picking one "correct" proportion — it's stratifying reported metrics by case difficulty. Covered 2026-09-15 (flagged as still-open for the actual train/val/test split — see open-questions file).
- **Quadratic vs. exponential growth, and where it actually bites.** `itertools.combinations(lst, 2)` produces `C(n,2) = n(n-1)/2` pairs — quadratic in group size, not exponential (that would be `2ⁿ`). Corrected a real terminology slip; matters for accurately describing why a few large groups (streets, or common house numbers) can dominate a pairs table even though they're a small fraction of the *groups* themselves. Covered 2026-09-16.
- **Concentration/blocking analysis: raw group-size histograms and quadratic-weighted pair contribution answer different questions.** A histogram of "how many groups have roughly this size" can look unremarkable even when a handful of large groups contribute the majority of `C(n,2)`-weighted pairs, since group count and pair count scale differently. The only way to actually answer "are my final pairs dominated by a few groups" is to sum the real contribution (`C(n,2)` for raw candidate pools, or direct counts for already-filtered output) from the top-N groups and divide by the total — not to eyeball a size distribution. Worked through twice this session (Case 1 street concentration, Case 2 house-number concentration) before landing on this. Covered 2026-09-16.
- **Ablating a component that's structurally constant across your whole candidate pool isn't a fair "does this matter" test.** If a bonus/feature is guaranteed to be present for every row (e.g. because upstream blocking already filtered to only rows where it's true), "removing" it in an ablation is mathematically equivalent to just raising the pass threshold uniformly — it doesn't tell you whether that signal discriminates between rows, since there's no variation to discriminate on. Only bonuses that vary (fire for some rows, not others) give a meaningful ablation result. Surfaced via a real case: `address_score` (always +0.05, guaranteed by `Address`-groupby blocking) and a buggy `is_extensional` bonus (effectively always +0.05, since 99.99% of the dataset shares the same value) both looked "significant" in an ablation, but for structural reasons unrelated to whether they discriminate. Covered 2026-09-16.
- **pandas `groupby()` with a list of column names vs. a bare string.** `df.groupby(["col"])` (a list, even length-1) yields tuple-shaped group keys when iterating (`(15,)`); `df.groupby("col")` (bare string) yields scalar keys (`15`) directly. Same grouping result either way, just a different key shape on iteration — easy to trip over if code expects a plain value. Covered 2026-09-16.
- **`pd.merge()`'s `suffixes` parameter vs. `pd.concat(axis=1)`.** `merge` automatically renames columns that collide by name between the two DataFrames being joined (`suffixes=("_a","_b")` → `StreetName_a`/`StreetName_b`), which only applies to columns present in both frames under the same literal name — a column like `original_id` that doesn't share a name with anything in the other frame passes through unsuffixed and needs a manual rename if you want consistent naming. `concat(axis=1)` has no equivalent auto-suffix behavior at all (duplicate names just coexist) and aligns rows by index, not position — needs `.reset_index(drop=True)` on both sides first if you just want "row N next to row N" regardless of original index. Covered 2026-09-16.
- **Jupyter/IPython only auto-displays a cell's literal last top-level expression** — it doesn't reach inside `for`/`if`/function bodies to auto-render intermediate values, even on the loop's last iteration. `df.head()` inside a loop silently computes and discards its result every time; need `from IPython.display import display` and an explicit `display(df.head())` call to render it. Covered 2026-09-16.
- **Python f-string debug/format mechanics.** The `=` specifier (`f"{expr=}"`, Python 3.8+) prints both the literal expression text and its value with no manual label string needed, and composes with format specs (`f"{expr=:.1f}"`). Format-spec cheatsheet: `.Nf` = N decimal places (fixed-point, rounds); `,` = thousands separator; `%` = percentage (multiplies by 100, appends `%`); `>`/`<`/`^` + width = right/left/center alignment. On a float, `int(x)` truncates toward zero while `round(x)` rounds to nearest using banker's/ties-to-even rounding and `f"{x:.0f}"` also rounds (ordinary, not banker's) while keeping float-formatting machinery — three different behaviors for "make this look like a whole number," worth choosing deliberately rather than assuming they're interchangeable. Also: `random.choices()`'s second positional argument is `weights`, not a sample count — need the `k=` keyword for that. Covered 2026-09-16.
- **"Positive/negative" (ground-truth match label) and "easy/hard" (classification difficulty) are orthogonal axes, not the same distinction.** A pair can be an easy positive (lightly corrupted, still obviously the same address), a hard positive (heavily corrupted, barely recognizable), an easy negative (two unrelated addresses, nothing alike), or a hard negative (Case 1/2's deliberately confusable pairs) — difficulty describes *how hard the pair is to classify correctly*, independent of what the correct label actually is. A real confusion this session: an early draft of a "positive dataset" generator was actually producing randomly-mismatched (non-corresponding) clean/corrupted pairs, which — once the label axes were untangled — turned out to describe an *easy negative* generator, not a positive one; the fix wasn't just correcting the sampling bug, it required first recognizing that "positive" and "easy" had been conflated in the first place. Covered 2026-09-16.
- **`.isin()` vs. `df.set_index(col).loc[list]` — two genuinely different lookup operations, easy to reach for the wrong one.** `.isin()` is a boolean set-membership filter: "does this row's value appear *anywhere* in my target list" — returns rows in the DataFrame's own existing order, automatically deduplicated (one row per unique value), with no way to preserve a target list's order or intentional duplicates. `df.set_index(col).loc[list]` is an ordered, duplicate-respecting label lookup: returns exactly one row per entry in `list`, in `list`'s exact order, repeating a row if its label appears more than once in `list` (and — if the DataFrame's own index itself has duplicate labels for a value — returning *all* matching rows for each occurrence). Covered 2026-09-17, after `.isin()`-based lookups silently discarded the intended pairing between two parallel `clean_ids`/`dirty_ids` lists (built together, position-for-position, to encode "these two ids are hard-negative partners") — the actual pairing information lived in shared list *position*, not in any property of the id values themselves, so a set-membership filter that discards position necessarily discards the pairing too.
- **`pd.merge(..., left_index=True, right_index=True)` matches on index *label equality*, not row position** — fundamentally different from `pd.concat(axis=1)`-style positional gluing, and a source of three separate real bugs this session (easy-negative self-pairing, hard-negative empty-result, positive-dataset row-count fan-out). Slicing operations (`.iloc[]`, `.loc[]`, boolean masks, `.sample()`) never reset a DataFrame's index on their own — the original row labels travel along with every selected row regardless of the new row order or any subsequent renaming of the source column. So if either side going into an index-matched merge still carries a *meaningful* label (an id from `set_index()`, or just the source DataFrame's original position from `.iloc[]`/`.loc[]`), the merge silently joins on "same label value," not "same draw" or "same position." Fixed each time via `.reset_index(drop=True)` on both sides immediately before merging, replacing the meaningful index with an always-unique `0..k-1` position so the merge becomes genuinely positional. One real exception, worth distinguishing from the bug: for the *positive* dataset specifically, matching by id-label equality is the *correct* relationship (a positive pair is, by definition, "same address, clean vs. corrupted side") — the bug there wasn't wrong matching, it was duplicate labels (from sampling positions *with* replacement) getting cross-multiplied by the join instead of paired one-to-one; fixed by sampling without replacement (see below), not by resetting the index.
- **`random.choice` vs. `random.choices` vs. `random.sample`.** `choice(seq)` returns one scalar element (no `k`). `choices(seq, k=n)` returns a list of `n` elements sampled *with* replacement — duplicates possible, independent per draw, no upper bound on `n` relative to population size. `sample(seq, k=n)` returns a list of `n` *distinct* elements sampled *without* replacement — raises `ValueError: Sample larger than population` if `n` exceeds the population size. `choices(seq, k=1)` is the closest equivalent to `choice(seq)` but still returns a one-element *list* rather than the bare scalar. Covered 2026-09-17, directly motivated by real behavior differences hit in `_generate_positive_dataset`/`_generate_hard_negative_dataset` (see above).
- **`set_index()`/`reset_index(drop=...)` mechanics, precisely.** `set_index(col)` *relocates* a column's values into the row index — doesn't delete the data, just moves where it lives (column → index). A subsequent `reset_index(drop=True)` then *discards* whatever the current index holds without restoring it as a column; plain `reset_index()` (default `drop=False`) restores it as an ordinary column first instead of discarding it. The two combined (`set_index(...).loc[...].reset_index(drop=True)`) is therefore "use this column as a label to look rows up by, then throw that labeling away once I'm done needing it" — useful specifically when you want the *lookup* behavior of a meaningful index but the *merge* behavior of a meaningless positional one afterward. Covered 2026-09-17.
- **`df["col"] == some_list` vs. `df["col"].isin(some_list)` — not interchangeable.** `==` against a list does elementwise *positional* comparison (row 0 vs. `list[0]`, row 1 vs. `list[1]`, ...) and requires matching lengths, raising `ValueError: Lengths must match to compare` otherwise; even where lengths happen to match, it answers a different question ("is row i's value equal to list position i's value") than membership testing. `.isin()` is a genuinely different operation — testing one column against an arbitrary-length candidate list for membership, returning a same-length-as-`df` boolean mask regardless of the candidate list's own length. Covered 2026-09-17.
- **Location-based (id-based) train/val/test splitting for a pairwise-matching dataset.** Split the *entity* id space first (non-overlapping by construction, since a split is a partition) — not the pair-*rows* directly, which have no concept of ids repeating across rows and so can't prevent leakage on their own. Then assign each pair-row to a split only if *both* referenced ids belong to that split's id-set, dropping any row whose two ids fall in different groups (a "boundary-crossing" pair). Positive rows (same entity referenced on both sides) never get dropped by this, since wherever that one id landed, both sides trivially match. Negative rows (two different, roughly independently-distributed entities) survive only with probability `≈ sum(p_group²)` across groups — a real, quantifiable, and potentially large fraction of negatives lost (measured at ~49% here, for a 68/17/15 split), not a bug to eliminate but a genuine cost of leakage-safe splitting worth sizing before accepting. Covered 2026-09-17.
- **Independently sampling "both sides" of a pair doesn't produce corresponding pairs.** Sampling a set of "clean" ids and a separate set of "corrupted" ids independently, then combining them (whether by `pd.concat(axis=1)`, which aligns by position/index, or any similar positional pairing) does not guarantee the two sides refer to the same underlying entity — you get `amount` clean rows glued next to `amount` unrelated corrupted rows. The correct pattern when you need "each thing paired with its own true counterpart" is a join/merge keyed on the relationship (here, `original_id`), which determines both sides from one selection instead of two independent ones. Covered 2026-09-16, caught via a genuine bug in the first `_generate_positive_dataset()` draft.
- **`LinearRegression` vs. `LogisticRegression`.** Regression predicts a continuous value and has no `predict_proba`/decision-boundary concept; classification (match/no-match here) needs `LogisticRegression`, which fits a linear decision boundary via a sigmoid and exposes `.predict()` (hard 0/1, thresholded at 0.5 by default for binary) and `.predict_proba()` (per-class probabilities). Covered 2026-09-21, caught as a real bug before ever running.
- **`.predict()` vs. `.predict_proba()`, and `model.classes_`.** `.predict()` returns already-thresholded hard labels, discarding confidence information; `.predict_proba()` returns the raw per-class probabilities the thresholding is built on top of (shape `(n_samples, n_classes)`, each row summing to 1) — needed for anything beyond a bare accept/reject call, e.g. sweeping the decision threshold or judging how confidently wrong a misprediction was. This shape is the *general* multiclass API, not something special-cased for binary — binary is just the `n_classes=2` case. `model.classes_` is populated automatically from the unique values seen in `y` during `.fit()` (sorted) and gives `predict_proba`'s column order — not something you set, something you read to confirm which column is which class. Covered 2026-09-21.
- **`classification_report`'s columns and averaging schemes.** Precision (`TP/(TP+FP)`, "of predicted-X, how much was really X") and recall (`TP/(TP+FN)`, "of actual X, how much was caught") are defined per class and are not symmetric between classes; F1 is their harmonic mean per class; support is just the class's row count in the evaluated set, not a performance number. `accuracy` is a single whole-dataset number (no per-class breakdown) and can be misleadingly close to a trivial constant-class predictor's score under imbalance. `macro avg` averages each class's metric unweighted (treats rare and common classes as equally important); `weighted avg` averages weighted by each class's support (ends up dominated by whichever class has more examples, and converges toward accuracy). Covered 2026-09-21, motivated by a real divergence in the project's own Step 1 results (macro F1 0.89 vs. weighted F1 0.96) exposing the model was meaningfully weaker on the rare "match" class than the blended weighted number suggested.
- **Quadratic (not linear) shrinkage of grouped candidate pools under a smaller sample — extends the 2026-09-16 "quadratic vs. exponential" lesson.** When a pair-generation step relies on `C(n,2)`-style within-group combinations (e.g. Case 1 hard-negative mining, grouped by street), subsampling the underlying pool by fraction `f` shrinks the *pair* count by roughly `f²`, not `f` — because it's not just fewer rows, it's fewer rows landing in the same group as each other. Confirmed empirically on this project's own data: a ~15%-sized id subsample retained only ~2% of the full pool's raw Case-1-style candidate pairs, matching `0.15² ≈ 0.0225` closely. The same underlying math also explained the original split-then-filter bug (train/val/test label-ratio mismatch, see Step 2 above) — worth recognizing as the same shape recurring in a new place, not a new phenomenon each time. Covered 2026-09-21.
- **Edit-distance metrics vs. token/n-gram-overlap metrics are fooled by opposite kinds of corruption — not the same signal at a different scale.** Levenshtein cares about position/alignment, so word-reordering (`"SPRUCE BLUE"` vs `"BLUE SPRUCE"`) looks like a heavily-edited, dissimilar string even when the content is identical. N-gram-set metrics (Jaccard/Dice/etc.) throw away position entirely, so reordering barely moves their score — but a single character substitution can be *worse* for them than for Levenshtein, since changing one character breaks every overlapping n-gram that touches it (verified: `"MAIN"`→`"MAON"` is Levenshtein-similarity ≈0.75 but bigram-Jaccard ≈0.2). Since this project's corruption pipeline is character-edit-heavy with no word-reordering, the n-gram metrics were predicted to be the shakier signal here specifically — worth checking against actual per-corruption-type results later (ties into the still-open "stratified evaluation by corruption type" question). Covered 2026-09-21.
- **`textdistance`'s algorithm classes take a `qval` constructor argument for n-gram size** (default `qval=1`, i.e. character-level/unigram) — no separate n-gram-generation helper function is needed; instantiate e.g. `textdistance.Jaccard(qval=2)` and call `.normalized_similarity()` directly on raw strings. Verified empirically that `Jaccard(qval=2)` on raw strings matches a manually-built-bigram-list Jaccard exactly. The pre-instantiated lowercase singletons (`textdistance.jaccard`, etc.) default to `qval=1`, which is why calling them directly on raw strings gives character-level rather than bigram results. Covered 2026-09-21.
- **Tversky index with default weights (`α=β=1`) is mathematically identical to Jaccard similarity** — Tversky is a strict generalization (`|A∩B| / (|A∩B| + α|A−B| + β|B−A|)`), and `α=β=1` reduces it exactly to Jaccard's formula. Verified empirically (identical scores on the same input, and identical fitted `LogisticRegression` coefficients on real data — `jaccard_street == tversky_street` etc.). Not a bug when it shows up as duplicate coefficients — it's two column names computing the same thing unless you explicitly pass non-default `ks=(α,β)` weights to `Tversky`. Covered 2026-09-21.
- **Dice, Overlap, and Cosine (set-based) collapse to the identical formula whenever the two compared sets are the same size.** All three normalize `|A∩B|` differently (`2I/(|A|+|B|)`, `I/min(|A|,|B|)`, `I/sqrt(|A|·|B|)` respectively) — but when `|A|=|B|=n`, all three algebraically reduce to `I/n`. Confirmed empirically on this project's `ZipCode` field specifically: always exactly 5 characters on both sides → always exactly 4 bigrams on both sides → `sorenson_zip == overlap_zip == cosine_zip` exactly in the fitted model, while the same three differ from each other on `StreetName` (variable length, no forced size equality). A genuine data-driven distinction, not a bug — worth knowing which "different" metrics are actually redundant on a given field before trusting a feature-importance ranking at face value. Covered 2026-09-21.
- **Levenshtein distance and Hamming distance are identical on a field that's always fixed-length with no insertions/deletions.** Verified empirically across all 15,102 training rows: `levenshtein_distance(ZipCode_a, ZipCode_b) == hamming_distance(ZipCode_a, ZipCode_b)` in every single row, with zero exceptions. Reasoning: Levenshtein's optimal edit path only benefits from insertions/deletions when they let it realign content more cheaply than direct substitution — with `ZipCode` always exactly 5 characters and never synthetically corrupted via insert/delete, the optimal path is always plain positional substitution, i.e. exactly Hamming's definition. `lv_zipcode_sim` and `hm_zipcode_sim` are the same feature under two names for this specific field, which is why their fitted coefficients came out identical. Covered 2026-09-21.
